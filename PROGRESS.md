- [x] **04 — Section titles.** Client's note: "Some sections have a small title above them and some don't. Following one rule — every section titled, or none — would look more deliberate." Two passes at this, both text-based, both wrong: first grepped only the `kicker` class name and thought Solutions/Use Cases hub had zero titled sections (wrong — they use `eyebrow` too, including compound classes like `class="eyebrow sheet-tag"`, plus nesting a shallow check misses). Second pass matched full section text and concluded every page was already 100% compliant — also wrong, because a section can *contain* the word "kicker" somewhere without that title actually belonging to *that* section, or a section can genuinely have zero title and a text-presence check won't catch it if it's just absent. Only trusted the result after checking the real DOM in a headless renderer per page (does this exact `<section>` contain a title element as a direct, non-nested child): real gaps were `contact.html`'s `contact-details` (address/email/phone block — no title) and, identically across all 6 use-case subpages, `case-story` (the before/during/after beats) and `case-metrics` (the 3 stat tiles). Fixed: added "How to reach us" above contact-details (new `.contact-details > .contact-kicker` rule to align its width to the detail grid below it); added "HOW IT WORKS" above case-story and "PRIMARY DECISIONS" above case-metrics on all 6 use-case pages, which required splitting each section's CSS into an outer plain wrapper + new `.case-story-grid`/`.case-metrics-grid` inner class carrying the actual grid layout (the kicker can't be a grid item alongside the 2-3 content cells without breaking the column count). Re-verified with the same DOM check after the fix: all 12 pages checked now 7/7, 6/6, or 4/4 titled, confirmed. **Not verified: Home** (`index.html`) — single ~460KB interactive scrollytelling page, not stacked marketing sections, and already its own separate rollout phase below Site-wide — check it there, not here.
- [x] **06 — Dashes in the copy.** Client's note: the text leans on long dashes, part of what makes it read machine-written. Grepped every `.html` file (not a sample) for `—`/`&mdash;`: 87 occurrences across 16 files. Read each with full sentence context before deciding the replacement — no blanket find-replace, since the right swap depends on the sentence (colon when the dash introduces an explanation/list, comma for a short clarifying clause, period+new sentence when both sides are full independent clauses, parentheses for a genuinely interjected aside). Also caught and fixed 4 numbered kickers on Trust & Security ("01 — SECURITY POSTURE" etc.) to use "01 / SECURITY POSTURE" instead, matching the "01 / 03" and "01 / PERCEIVE" numbering convention already used elsewhere on the site (Why RackTrack, Solutions) rather than inventing a third style. Deliberately left one instance alone: a `// ponytail:` JS code comment in `use-case-security-vulnerability-teams.html` — not copy, not user-facing, touching it would be pure scope creep. Verified with a final sitewide grep after: zero em-dashes remain anywhere except that one comment.
- [x] **05 — Alignment and spacing system.** Client's note: "settle the alignment and spacing values once, and roll the same system across all pages." Measured real computed spacing (padding/margin/gap, not eyeballed) across every page in headless Chromium: `main → section` gaps, per-section padding-top/bottom, and heading positions, all 12 main pages. First measurement pass surfaced two apparent outliers — a 517px gap on Trust & Security and a 108px gap on Solutions — and both turned out to be false alarms on closer check, which is exactly the kind of premature "found a bug" call this file has had to walk back twice already this session, so worth recording how each was actually ruled out: the 517px gap is real content (a captioned hero image + the numbered 01–04 index nav) sitting between the hero and the first section, not empty space; the 108px gap is `.solutions-page .schematic-section { margin: 108px auto 0; }`, a deliberate, already-commented design choice ("Sits between Sheet 01's 1440px and Sheet 03's 1280px — matches the page's standard section scale instead of being its own one-off width"). All 6 use-case subpages measured byte-for-byte identical to each other on every gap and padding value — one system, already applied uniformly. **Verdict: no bug found.** The only remaining variation is hero `padding-top`/`padding-bottom` (110–156px range across pages), which tracks each hero's structurally different composition (circular image / split image / full-bleed image / no image), not carelessness. Client confirmed: leave as-is rather than force one hero padding value across genuinely different layouts.
- [x] **Known open bug (not in the original 27).** "Use Cases"/"Resources" rendering on a lower row than the other nav links on all `*-page.html` pages that use the shared header (not just the 6 use-case pages — confirmed on the M&A migration page). The earlier "no longer reproduces" note here was wrong — it was never actually re-tested in a browser, just assumed fixed as a side effect of the nav pass. Real root cause, found by rendering in headless Chromium and diffing computed styles: `.site-nav` is `display:flex` with the browser default `align-items: stretch`, so direct `<a>` children stretch to the row's full height for free — but Use Cases/Resources are wrapped in `.nav-item` divs, and the `<a>` *inside* that div is one level too deep to inherit the stretch, so it stayed at its tiny intrinsic line height and sank to the bottom of the now-taller `.nav-item` box next to the plain links. Fixed with `.nav-item > a { display: flex; align-items: center; height: 100% }` in `styles.css`, verified with real Playwright renders (bounding rects + screenshot) before and after, not just a source read. Also gave the M&A migration page's hero a matching fix: it was the only `case-hero-*` variant with a big empty gap on the right, because it inherits the shared `min-height: 92dvh` from the 2-column hero layout but drops to 1 column (for its full-width before/after image strip below) without anything to fill that height. Scoped `min-height: 0; row-gap: 56px; align-items: start` to `.case-hero-migration` only — other 5 use-case pages untouched.

- [x] **10 — Grid-pattern background.** Client's note: "letting go of the grid pattern behind the pages — it's another thing that reads AI-generated." Found every instance sitewide (17 separate CSS declarations across 13 selectors, not a single global rule — the pattern was hand-copied into hero overlays, CTA overlays, the cabinet-reader demo stage, and one shared body-background rule covering Solutions/Use Cases hub/Contact/all 6 use-case pages). Removed all 17. Two had to be handled carefully instead of a blind `display:none`: `.why-hero-field` and `.contact-hero-field` both have a separate `::after` pseudo-element (an unrelated decorative circle/border) that would have been silently deleted too if the parent got `display:none`, since a hidden element hides its pseudo-elements with it — caught this before applying it broadly, and used surgical property removal on those two instead. Verified with screenshots on Why RackTrack, Solutions, Contact, and the Network use-case page after: clean flat backgrounds, no layout regressions.

- [x] **11 — Fonts.** Client's named example: the "SIX TEAMS, ONE SWEEP" heading. That's an `.eyebrow`-class kicker, and the site has **seven** near-duplicate kicker classes (`.why-kicker`, `.case-kicker`, `.contact-kicker`, `.ab-kicker`, `.tsec-kicker`, `.ap-kicker`, `.eyebrow`) that had all drifted slightly apart: `.eyebrow` was 12px/weight 760/letter-spacing 0 (the exact drift named), `.contact-kicker` was 10px, and the rest ranged 0.08–0.13em letter-spacing. Converged all seven to one spec — 11px/700/0.13em/uppercase, matching `.case-kicker` since it's the most-used pattern (identical across all 6 use-case pages already). Three of the seven shared their font rule with unrelated micro-labels (form field labels, card index numbers, dense demo-UI captions) — split those out first so only the actual section-kicker changed, not everything nearby. Verification surfaced two bugs beyond the kicker fonts, both real and both fixed: (1) Solutions' `.eyebrow` still measured 12px after the base fix — a second, more specific `.solutions-page .eyebrow` rule was overriding it, found and fixed. (2) Every hero kicker inside `.case-hero` (all 6 use-case pages) was rendering at **19px** instead of 11px — `.case-hero p{font-size:19px}` (meant for the body paragraph) was winning over `.case-kicker` on specificity since both are `<p>` tags in the same container; this is a real bug from earlier in this session that I found the symptom of at the time but never actually traced to its cause. Fixed with `.case-hero p:not(.case-kicker)`.

- [x] **09 — Heading alignment.** Client's note: "some centered, some left... one alignment across the site would tidy this up." Rendered every `h1`/`h2` on all 13 main pages (not `main > section` shallow, every heading regardless of nesting) and read `text-align` + left position directly, not from CSS source. Result: 24 of 25 headings already `text-align: start`, consistent. The one exception — Use Cases hub's opening H1 — is `text-align: center` inside a deliberately symmetric cinematic hero (centered headline with 6 floating role tags arranged around it, full-bleed photo background); nothing else on the site is built this way, and forcing it left would leave centered text off-balance without restructuring the whole composition. Client confirmed: leave it. **Same audit surfaced two unrelated real bugs**, both fixed: (1) all 3 `<b>ANSWERED</b>` tiles on the Security use-case page were rendering as giant spinning gradient circles instead of small text labels, and the 3 on Compliance were compressed into invisible 1px lines — both caused by dead CSS for a `.case-scene` decorative widget removed from the HTML long ago (`.case-page[data-scene="radar"] b` / `.case-page[data-scene="ledger"] b`, same bug class as the migration-page font leak found earlier this session, just never swept for the other 5 `data-scene` variants). (2) The Incident-Responders hero was shifted 144px right of its 5 identical siblings — `.case-page[data-scene="timeline"]` leaking `padding: 0 10%` onto `<body>`, same root cause. Swept **all six** `data-scene` variants this time (not just the one that broke), including a Network page SVG diagram leak that was wrong in computed values but happened not to be visibly broken (documented, not silently left). All six rescoped from `.case-page[data-scene="X"]` to `.case-page[data-scene="X"] .case-scene`.

- [x] **08 — CTA style/height unification.** Client's note: "The CTA blocks change from page to page, and some feel oversized. One CTA style at one height, reused everywhere, would be cleaner." Measured all 9 CTA blocks sitewide (Why RackTrack, Solutions, Trust & Security, Use Cases hub, and the shared `case-cta` on all 6 use-case pages). Button style (border-radius, font-size) was **already** identical everywhere — nothing to fix there. Padding was not: ranged 78px–164px, and Why RackTrack's CTA had `min-height: 100dvh`, forcing it to a full 900px viewport-height block regardless of content — exactly the "some feel oversized" complaint, and also directly satisfies **item 21** ("Why RackTrack: CTA runs much taller than the others") from the per-page list below, so that item is done too as a side effect. Standardized every CTA's vertical padding to 90px and removed the forced full-viewport height. Heights now range 310–664px, tracking each CTA's actual headline length (not artificially forced), down from the previous 286–900px spread. Use Cases hub's closing CTA (`uc-close`) keeps a transparent background instead of the shared light-blue tint — that's correct, not a miss: the whole page is dark-themed and the light tint would look broken there; button style already matches.
